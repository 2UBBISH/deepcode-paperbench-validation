# Reproduce this paper — brief for the coding session

You are a coding agent working alone in this directory. Read this file first, then `paper/paper.md`
(the paper), `paper/addendum.md` (clarifications from the benchmark authors) and `paper/blacklist.txt`.
Do not read anything outside this directory except what you fetch from the internet yourself.

## Task

Reproduce as many of the paper's **core contributions** as you can: the methods it proposes, the baselines it
compares against, and the experiments in the main text (Section 5). Anything introduced only in the appendix
is out of scope; details that the main text defers to the appendix (hyperparameters, formulas) are in scope.

Partial credit is given per component, weighted by importance to the paper. Prioritise: the proposed methods
first, then every baseline the paper compares against (each as its own class or function with a training
procedure), then the experiment scripts that produce the paper's tables and figures. Do not skip a baseline
because it is "just a baseline": a baseline that is not implemented scores zero for its whole branch.

## Inputs

- `paper/paper.md`, `paper/paper.pdf` — the paper (ICML 2024, *Sequential Neural Score Estimation*).
- `paper/addendum.md` — read it carefully; it names the libraries and repositories the benchmark expects you to
  use for specific pieces (`sbibm` for NPE/SNPE/C2ST, the `mackelab/tsnpe_neurips` repository for TSNPE and the
  neuroscience problem) and says which results are not expected to be replicated.
- `paper/resources/tsnpe_neurips.zip`, `paper/resources/pyloric.zip` — snapshots of the two repositories the
  addendum names, provided so you need not fetch them. You may unpack them to `paper/resources/` and reuse code
  from them where the addendum says so; cite the origin in your README.
- `paper/blacklist.txt` — the paper's own codebase. **Never open, fetch, search for or reuse it.** Everything else
  on the internet is allowed (docs, `sbibm`, `sbi`, PyTorch).

## Output

Write everything under `submission/`, which must end as a git repository (`git init` there, commit as you go,
commit at the end; untracked files are deleted before grading). Rules:

- Source code only; no datasets, checkpoints or heavy artifacts committed (< 1 GB total). Synthetic data is
  generated by the code from seeds.
- `submission/reproduce.sh` at the root: a script that, run from the submission directory on a fresh
  Ubuntu 24.04 container with Python, installs what is needed and runs your experiments end to end, writing
  results (tables/figures) under an output directory. It will not be executed for this grading (code-only
  grading), but it must be a real script that would work; relative paths only.
- `submission/README.md`: what you implemented, how the code maps to the paper's parts (method, baselines,
  each experiment), what you did not implement and why, and what `reproduce.sh` produces.
- Target a **CPU-only** machine: default sizes and step counts should finish there; expose scale knobs.
- Python 3.10+, `pyproject.toml` or `requirements.txt` with pinned versions.

## Working rules

- One session, no fixed time limit; stop when you judge the reproduction complete or further work has
  diminishing return. Record in the README the wall time you used.
- No hidden helpers: everything the grader needs must be in `submission/`.
- Do not simplify a method silently. If you replace a step by an easier one, say so in the README and in a
  code comment at the spot.
- Keep a short log of decisions the paper leaves open (which you chose and why) in `submission/DECISIONS.md`.

When you are done, stop. The owner will grade the submission separately.
