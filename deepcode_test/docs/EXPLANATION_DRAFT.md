## 一、裁判的可信度

论文用 OpenAI 的 o3-mini 当自动评分裁判。我们没有 o3-mini,换成了 DeepSeek-V4-Pro,
**但评分流程用的是 PaperBench 官方同一套 SimpleJudge 脚手架,只换了底层模型**。

为验证替换可靠,跑了 PaperBench 官方的裁判考核(judge_eval):拿人类专家逐题批过的
标准答案考我们的裁判,F1 = 0.685 —— 与 o3-mini 在**同一批题目**上的 0.687±0.017
落在同一区间(我们单次、对方 15 次分布,故只说"落在其波动区间内",不说"水平相同")。

更重要的是方向:逐题比对发现**我们的裁判偏严**(人类给过 54% 的题,它只给过 45%),
而 o3-mini 偏松。**所以我们报出的所有分数都是偏保守的估计** —— 若结果比论文低,
有一部分归因于裁判严格,不能全算系统的问题。

**适用边界**:同一裁判下的相对比较有效;绝对分数不与论文数字直接对标。

## 二、rice:跑通流程的测试(shakedown)

### 我们对开源版做了什么修改(工程缺陷修复,不碰方法)

开源版 DeepCode 在非官方环境下跑不起来,我们逐一修复:

- **配置类**:官方 init 不生成自家流水线的 MCP 工具服务器配置(7 个需手工补,
  官方文档还漏列 1 个);裁判侧模型上下文表与二级解析器写死 OpenAI 模型,改为可配置;
- **兼容类**:实测发现国产模型(Kimi)对**带连字符的工具名**无法产生结构化调用
  (A/B 裸 API 证实),导致下载、文档分段等环节的工具全部静默失效 ——
  在工具注册层做名字规范化;
- **健壮性类**:仓库下载环节的提示词是从未接线的死代码(全仓库仅定义、无引用),
  按真实工具面重写;下载/分段的"成功"判定原本不校验产物落盘,补校验与 fail-fast;
- **协议补齐类**:论文声称"浏览网页时强制执行源码黑名单"防抄袭,
  **开源代码里却无任何黑名单实现** —— 按 PaperBench 官方黑名单文件补上了这层拦截。

**核心方法(蓝图规划、CodeRAG 索引与检索、写码循环)的逻辑与提示词一概未动。**
修的全是"接不通",不是"改方法"。

### rice 的结果与定位

无 CodeRAG **43.3** 分,有 CodeRAG **60.5** 分(**+40% 相对提升**)。
论文声称 CodeRAG 对非顶级模型约 +70% 相对提升 —— **方向与量级一致**。
且在同一篇 rice 上,论文里 Claude Code 仅 37.9、Cursor 41.9,
我们用便宜国产模型得到的 60.5 **高于全部商业工具**。

但 rice 线只当**流程验证**,不当正式结论:60.5 那次是跨多轮拼装、中途换过模型、
参考语料经人工筛选、仅单次运行。故 rice 定位为"跑通工具、挖出缺陷的测试",
正式测量另起炉灶。

## 三、fre:正式端到端测量

选 fre 因为论文对它参考数据最全(商业工具对比表、换底座阶梯图均有)。三方设定:

- **锚点**:Claude Code 本体(Sonnet 4.5,thinking 开)按 PaperBench 官方任务书
  原文复现 fre,全程无人工提示、实际离线完成(有联网工具但一次未用,
  事后审计 transcript 确认未触碰论文官方代码)。**单次即可**:论文商业工具表本身
  就是单次成绩;且对照实验显示两次独立运行产出逐字节相同的 2,657 行代码,
  方差近乎零。对应论文 Claude Code @ fre = **0.6286**。
- **被测**:DeepCode + DeepSeek-V4-Pro 完整流水线(含 CodeRAG,零人工语料筛选),
  独立三轮,其中一轮因下载环节失败作废,**有效两轮**。
- **裁判**:恒定 DeepSeek-V4-Pro + 官方 SimpleJudge,code_only(只评代码不运行)。

## 四、结论(按判定规则回填)

**判定规则**:论文自己同一配置跑三次可差 0.15,故 **±0.15 内的差距一律不下结论**。

- 若 DeepCode 两轮均分明显高于锚点(差 >0.15):
  "同一裁判、同一论文、同一协议下,DeepCode+国产模型显著超过裸 Claude Code,
  与论文'脚手架带来大幅增益'的主张方向一致;且我们的裁判偏严、未启用论文的
  执行自修复层,这是保守下界。**该效果可以信赖**(方向层面;绝对分不与论文直接对标)。"
- 若差距 ≤0.15 或为负:
  "我们的条件下未能复现论文声称的显著增益。已知差项(裁判偏严约 9pp、
  无执行自修复层 4~6pp)不足以解释全部缺口时,**该效果存疑**;
  底座档位不预设(V4-Pro 论文无参考值),由其得分按 Figure 5 阶梯反读——
  若同时得出'V4-Pro 仅中档',则'方法失效'与'底座不足'无法区分,需换更强底座定论。"

**附:V4-Pro 档位判读(实验产出之一,非前提)**:校正后 ≥0.7 → 前沿档;
0.45~0.6 → 中档;≈0.3 → 与 R1 无实质差别。**不得预设"底座弱"作为低分借口** ——
旁证(裁判 F1 与 o3-mini 打平、规划一次过、索引零 JSON 失败)反而偏正面。

## 五、诚实边界(对外必讲)

1. 论文的 **1.34× 架构增益**(DeepCode 0.8435 vs Claude Code 0.6286,同为 Sonnet4.5)
   我们**验证不了** —— 需要 Sonnet 4.5 接入 DeepCode,而其无法作为 API 使用。
   我们的对比混着模型差,只做方向判断;
2. 单篇论文(fre)+ 有效两轮,样本量小;
3. 裁判与被测同为 DeepSeek,存在自偏风险(锚点是 Claude 产物,该风险无法被锚点校正);
4. 我们修复后的 DeepCode 强于论文时点的开源版(见 §二清单),
   分数含工程修复的贡献 —— 但这些修复对任何底座模型都同样必要;
5. **我们未启用论文的"沙箱执行自修复"层**(论文 §消融:agent 运行生成代码的入口点、
   自动修变量名笔误/缺依赖/参数错,带来 +3.7~6.5pp)。我们的写码 agent 在 indexed
   模式下无 execute 工具,收尾验证也按书面决议未启用(strict_outcomes=False)。
   → 论文的 0.8435 含此层贡献,我们的成绩不含 —— 是"若我们偏低"的已知差项之一。
   注意:**评分口径不受影响**(论文所有分数也只用 Code-Dev 协议判,不执行提交后的代码;
   执行只发生在其生成过程内部);
6. **Code-Dev 口径本身的天花板(论文未承认的局限)**:
   论文 §4.1 原文 "follows the PaperBench **Code-Dev protocol**, which focuses on structural
   and functional correctness and **does not include post-submission reproduction**",
   判的是 static correctness / dependency validity / project structure / **algorithmic fidelity**
   四项静态指标(fre 共 306 条 Code Development 叶子,由论文作者与 PaperBench 共同制定)。
   → 该口径能证明"代码是否忠实实现了论文所述算法",**不能证明"跑起来能得到论文的数字"**。
   一份代码可通过全部静态条目,却因某处维度/符号写反而完全训不出来。
   论文 §6 讨论了模型效率、自进化等挑战,**未讨论此局限**。
   我们与论文同口径,故**对比公平**;但双方共享这个天花板。
   若要验证真实效果,需另做 GPU 复跑(PaperBench 的 Execution + Result Match 维度),
   本次范围之外。附:论文未说明选择 Code-Dev 的理由;客观原因是 20 篇深度学习论文的
   完整复跑是几百至上千 GPU 小时量级。

## 六、关于"论文证明了什么"的定性(2026-08-27 全文查证)

**论文全篇零证据表明生成的代码能实际运行并复现论文结果**,具体:

- **只在 PaperBench 上评测**,未在 SWE-bench / HumanEval / MLE-bench 等会真实执行代码的基准上评测;
- **无执行准确率、pass@k、单元测试通过率**等任何执行类指标;
- **无任何案例研究**证明某篇论文的生成代码真的跑出了原结果(附录 A.2 仅展示代码结构与片段);
- §3.3 的 "Sandbox Execution" 是**入口点冒烟测试**,原文 "attempts to execute the **main entry points**
  of the repository, using **automatically generated test data**",非完整训练;
  且"自动生成的测试数据"如何生成、是否覆盖论文实验配置,论文未说明;
- §6 讨论了(1) Agentic Capability and Computational Efficiency、(2) From Episodic to Evolving Agents、
  (3) Dynamic Planning and Adaptability 三项挑战,**未将"评分不执行代码"列为局限**。

**因此论文成立的主张是**:能自动产出结构完整、依赖齐全、**算法实现忠实于论文描述**的代码库,
忠实度经人类专家数百条细则逐条检验,显著高于通用编码工具。
**论文未成立的主张是**:该代码跑起来能得到论文的数字。

### ⭐ PaperBench 不是用得不好,而是论文只用了它的三分之一

PaperBench 完整协议有三类评分维度,fre 共 437 叶:

| 维度 | fre 题数 | 含义 | 论文用了吗 |
| --- | --- | --- | --- |
| Code Development | **306** | 代码写得对不对(静态) | ✅ 唯一使用 |
| Code Execution | **124** | 代码跑不跑得起来 | ❌ 未用 |
| Result Match | **7** | 结果与论文趋势是否吻合 | ❌ 未用 |

**"不执行"是论文的选择,不是数据集的缺陷。** 我方与论文同口径故对比公平;
且我方早已为完整复跑做好准备(`pb-reproducer` 镜像已修通 python/pip/jupyter/PEP668、
NVIDIA 容器运行时已验证、命令见 `EXECUTION_PLAN.md` §4),仅按计划搁置。

**可选扩展(高价值)**:拿 DeepCode 产物跑 Execution 维度,可回答**论文自己没回答的问题**——
生成的代码到底跑不跑得起来。即便只测 fre 一篇也是原创补充。
Execution 维度只考"能否装依赖、能否启动脚本不报错",**不要求训练至收敛**,
8GB 笔记本 GPU 足够;代价约 ¥60 判分 + 1~2h 风扇高转。
