# 总结论:DeepCode × DeepSeek-V4-Pro 独立验证

> 2026-09-01 · 全部实验收官后的汇总。数据细节见 `../fre/RESULTS.md`、`../rice/RESULTS.md`,
> 工程发现见 `FINDING_prefilter_silent_failure.md`,对外页面见汇报 Artifact。

---

## 1. 事实

同底座(DeepSeek-V4-Pro)、同任务书、同裁判,唯一变量 = 有没有 DeepCode 脚手架:

| 论文 | 裸跑(Claude Code 壳) | DeepCode 两个完整轮 | 实测倍数 | 论文声称 |
| --- | --- | --- | --- | --- |
| fre | 0.4817 | 0.5184 / 0.4246 | **0.98×** | 1.34× |
| rice | 0.4680 | 0.5447 / 0.4374 | **1.05×** | 1.95× |

- 两篇论文里,**裸跑的分数都落在 DeepCode 两轮之间**
- 组内轮间波动(0.094 / 0.107)是组间差距(0.010 / 0.023)的 **9 倍 / 4.6 倍**
- **结论:在 V4-Pro 底座上,DeepCode 脚手架没有可测得的增益。**

## 2. 结果可信度(五项核验,2026-09-01)

1. **算术**:8 份提交的报告分 = 按权重逐层重算,误差 < 1e-9
2. **配置**:同一批的判分配置逐字段一致(judge/model/temperature/code_only/叶数)
3. **rubric**:同一论文的各份判的 178/306 条叶子要求逐条相同
4. **卷子**:判分器解包的 tarball 与摆卷的 py 文件名集合一致
5. **分布**:叶级得分全为 0/1 二值,无异常聚集

已知偏差:裁判文件选择环节存在静默失败(2~9% 叶子被误判为"无提交文件"),
**只压低、不抬高**,且各组同向 —— 全按上界修正后 fre 0.95×、rice 1.05×,主结论不动。
分数只可同裁判内部相对比较,不可与论文数字直接相减。

## 3. 为什么脚手架没用 —— 四条机制,全部有实测锚点

### ①(2026-09-02 修订)条件性增益假设已被正式数据否定

原假设"模型越强脚手架越没用"的弱模型端证据只有拼装试点(Kimi +40%)。
正式协议补测后(rice,同壳同裁判):

| 底座 | 裸跑 | DeepCode 两轮均值 | 自身增益比 |
| --- | --- | --- | --- |
| DeepSeek-V4-Pro | 0.4680 | 0.4911 | 1.05× |
| Kimi-K2.7-Code | **0.4633** | 0.3788 | **0.82×** |

- 裸跑 Kimi ≈ 裸跑 V4-Pro:**我们从未真正测到弱模型**,K2.7-Code 本身已是同档
- 脚手架在 Kimi 上为**负增益**;试点 +40% 系人工筛语料的拼装轮工件,不再引用
- 四条裸跑基线(3 个模型、2 篇论文)全部聚在 **0.46~0.48** —— 
  这个"裸跑地板"的稳定性本身就是结论:**通用壳 + 2026 年主流模型,
  论文复现能力已趋同;重编排在其上无增益(0.82×~1.05×),只有成本与失败面**

### ② "计划-填充"架构把一次规划失误放大成整轮损失

DeepCode 在 Phase 5 一次性定死文件树,写码循环只负责填空壳。
fre 两轮的规划都漏掉了三个对比基线(GC-IQL/GC-BC/OPAL 全 0),
后面几百轮写码**结构上不可能补救** —— 反事实补上后 trial1 达裸跑的 1.354×,
与论文声称的 1.34× 几乎一致。**架构增益可能真实存在,但被规划的单点故障整个吃掉。**
裸跑边读论文边决定写什么,读到 baselines 章节自然就写了。

### ③ clean-slate 循环让强模型付出无谓的冷启动成本

每写完一个文件就清空对话、重建 43k token 的上下文。V4-Pro 这类思考型模型
每次冷启动要重新推理整个项目(实测 6.8 分钟/文件,rice),
且会陷入"思考写满、正文为空"的空响应循环(实测连续 11 次)。
裸跑一场连续对话,越写越顺:同一篇 rice,裸跑 18 分钟 ¥2,DeepCode 5 小时 ¥31~45。
**产出对比:DeepCode 写 12,583~25,630 行,裸跑 4,173 行 —— 分数反而是裸跑居中。**
写码循环从不调用 command_executor:只生成、不执行、不验证,多写的代码是多写的猜测。

### ④ 每加一层编排,就加一层静默失败面

本次验证实锤的静默失败(全部"失败被标成功、流水线毫无察觉"):

| 位置 | 缺陷 | 后果 |
| --- | --- | --- |
| CodeRAG 预筛 | max_tokens=2000 截断 → 回退全量索引 | 大仓库索引 18× 耗时,google-research 需 140h |
| 规划兜底 | 超时 3 次后 coerce 出假计划,标 completeness=1.0 | 整轮照假计划写空壳 |
| 仓库下载 | 单次失败无重试,汇总照报 success | 语料缺失无人知晓 |
| 判分文件选择 | LLM 返回空 → `<files>` 空 → 判 0 分且 valid=True | 分数系统性偏低 2~9% 叶 |

裸跑没有这些层,也就没有这些失败面。

## 4. 对"是不是新版 agent 更聪明了"的回答

**方向对,归因要修正。** 裸跑组的"大脑"也是 DeepSeek-V4-Pro,不是 Claude ——
Claude Code 在裸跑组里只是一个**通用 agent 壳**(读文件/写文件/执行的循环)。
所以结论不是"Claude 模型变聪明了",而是:

> **现代强模型 + 极简通用壳,已经内化了专用脚手架想外挂的能力**
> (自主规划、按需读参考、增量写码)。DeepCode 这类为"需要搀扶的模型"
> 设计的重编排,在强模型上只剩成本与失败面。

时间线上讲得通:论文实验用的是 R1 时代的非顶级模型对照(+70%)和
Sonnet 4.5(1.34×~1.95×,**我们无法复测**,无 API);
而 2026 年的 V4-Pro 在 agent 任务上已是另一档。
**脚手架的价值随模型迭代折旧** —— 这可能是这类论文的普遍宿命。

## 5. 不能说的话(边界)

- 不能说"论文造假":底座不同(论文 DeepCode 侧用 Sonnet 4.5)、
  开源版工程状态可能不同于作者内部版、裁判不同且偏移不可标量化
- 能说的最强表述:**开源发布的这份代码,在我们可获得的最强同底座对照下,
  无法复现论文声称的架构增益;且其多个核心组件在真实运行中静默失效**
- 单篇×2、每组 n=2~3,统计效力有限;Code-Dev 口径只审代码不执行,天花板双方共享

## ⑦ 2026-09-03 追加:结论依赖裁判 serving(必须最先读)

本文以上全部结论均在 **SiliconFlow 服务的 DeepSeek-V4-Pro 裁判**下得出。
用 **Paratera 服务的同名模型**重判全部 11 份有效提交后:

- **fre:结论不变**。DeepCode/裸跑 0.98× → 0.81×,两裁判一致无增益。
- **rice:结论翻转**。V4-Pro 线 1.05× → **2.58×**;Kimi 线 0.82× → **1.65×**。裸跑从 0.47 跌到 0.15~0.19,DeepCode 只跌 0.04~0.14。
- 诊断:两裁判输入 token 几乎相同、输出 token 减半、45 个叶 1→0;对"通用可配置实现是否算已实现"判断相反。
- **JudgeEval 仲裁(已跑)**:SiliconFlow F1 0.685 vs Paratera 0.719,通过率与偏向完全相同,同一提交 16% 叶级分歧;差异在噪声内,且样本(作者仓库)不覆盖分歧区间 → **无法裁定哪个裁判对**。

因此 §① "无增益" 的正确表述是:**"在 SiliconFlow 裁判下无增益;在 Paratera 裁判下 rice 有增益、fre 无增益"**。
§⑥ 逐份失分表仍然有效(它描述的是 SiliconFlow 裁判看到的丢分位置)。
另:修复验证轮 fx1/fx2 作废(提示词含评分元知识),"修复①②③④能否恢复增益"**未得到有效检验**。
