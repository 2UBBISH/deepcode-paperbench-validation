## 5a-2. ⚠️ 论文声称的黑名单 vs 开源代码的实际(2026-08-26 实证)

**论文 §4.1 Task Execution 原文**:
> "To ensure that generated solutions stem from algorithmic reasoning rather than retrieval,
> a **source code blacklist is enforced during execution**. This protocol precludes access to
> the authors' original repositories and known third-party implementations **during web browsing**."

**开源实现的实际**:DeepCode 全仓 grep `blacklist` **零命中**,不存在任何黑名单逻辑。
论文声称的这条保护**在发布的代码里没有对应实现**。

**实证触发**(trial 1,2026-08-26 20:31):参考挖掘相位的 V4-Pro 通过 `fetch` MCP
**抓取了 `https://github.com/kvfrans/fre`**(114 次 fetch 中的第 18 个)。
我方的 git `insteadOf` 封锁只覆盖 git 协议,**挡不住 HTTP 抓取** —— 这个已知缺口被真实触发。

**结论(影响实验口径)**:给参考挖掘的 fetch 加 URL 黑名单拦截,**不是我方额外加料,
而是补上论文声称使用、但开源代码缺失的协议**。不加则跑的不是论文描述的实验;加了才是保真。

**口径差须披露**:论文的黑名单更宽(还含 "known third-party implementations"),但**未公布名单**。
我方只能执行 PaperBench 的客观标准 `data/papers/fre/blacklist.txt`(仅 `kvfrans/fre`)。
本轮 V4-Pro 抓过 `ikostrikov/implicit_q_learning`、`denisyarats/exorl`、`Farama-Foundation/D4RL` 等
方法级依赖 —— 按 PaperBench 规则**合法**,按论文那句话**可能不合法**。此差异写入结论。

## 5a-3. 裁判校正:三条结论 + 两条对既有判断的修正(2026-08-26 深挖,已独立验算)

### ⚠️ 修正一:"precision ≈ recall,所以无系统性偏松偏严" —— **错,是 macro 平均造成的假象**

`judge_eval_results_rice/.../results.json` 记录 macro precision **0.6913** / macro recall **0.6905**,
几乎相等,曾据此判断"误判在正负两个方向大致对称"。**这个推论不成立**:两个数是**两类别的宏平均**,
而两类偏差方向**相反、在平均里互相抵消**。

由 accuracy 与 macro recall 反解混淆矩阵(唯一解,且反算 macro precision 精确吻合到 1e-6):

| | 值 |
| --- | --- |
| TP / FP / FN / TN | **60 / 20 / 36 / 62** |
| 正类召回(该给分时给分) | **0.625** |
| 特异度(该扣分时扣分) | **0.756** |
| 我方判通过率 | **0.449** |
| 人工标注通过率 | **0.539** |

**假阴 36 个 vs 假阳 20 个 —— 少判 16 个本该通过的叶子,净偏严 9.0 个百分点。**
→ **教训(易再犯)**:macro 平均会掩盖类别间的反向偏差;判断裁判偏松/偏严必须看
**通过率对比或逐类召回**,不能看宏平均的 precision/recall 是否相等。

### ⚠️ 修正二:"我方裁判约 gpt-4o 级,低于论文的 o3-mini" —— **数据在别处,结论反了**

曾因 `experiments/judge_eval/judge_eval_results/` 为空而无法引用 o3-mini 数字(**该目录确实为空,这点无误**),
遂按 F1 0.685 推断"低一档"。但 o3-mini 的可比数据在 **`experiments/judge_max_depth/results.zip`**:
内含 **15 棵 o3-mini-high 对 rice/0 同一份提交的原始判分树**,节点 ID 与人工标注 1:1 对应。
离线打分(**¥0**):**o3-mini-high 在同样 178 叶上 F1 = 0.687 ± 0.017,我方 0.685 —— 统计上无差别。**
"低一档"是拿我方**单篇**数字比论文**五篇聚合**造成的错觉;正确对照是 Code Development 那一栏(0.7198),
而非 Overall(0.8266,混入了 code_only 根本不含的 Code Execution 与 Result Analysis)。

### 结论三(维持并强化):**数值校正不可行,锚点降级为"序关系参照"**

- n=1 锚点的偏移量 **95% CI = ±0.499**(即便假装 σ 已知也有 ±0.227),**比论文 Table 1 全部工具的跨度还宽**,
  既分不清正负、也与零无法区分;
- **偏移不是标量**:对照人工标注,我方裁判在不同 rubric 章节的偏差从 **+0.414(环境搭建)到 -0.406(精炼方法)**,
  Cochran Q=49.5(df=7),**I²=85.8%**。一份提交的实际偏移取决于它恰好满足哪些条目 —— 而这正是
  Claude Code 与 DeepCode+V4-Pro 最大的差别所在,且该差异方向**对 DeepCode 有利**;
- 加法与乘法校正在我方数值域内**都会越界**(乘法把 0.605 推过 1.0;加法在锚点 >0.72 时同样),
  两者结果差 **0.085**,与轮间标准差同量级。若非要做,只有 logit 位移在 [0,1] 上封闭;
- **自偏无法被锚点消除**:锚点是 Claude 产物,估不到"DeepSeek 判 DeepSeek 自己写的代码"那一层。

**→ 采用口径**:锚点用于**同一裁判下的相对比较**(DeepCode+V4-Pro vs 裸 Claude Code),
**不用于**把分数换算到论文的 0.8435/0.6286。此前会话中"够用于比相对差距、不够用于直接对论文数字"的判断**正确且保留**。

## 5c-2. 锚点 v1/v2 对照实验结论:**预算不是约束,v1 未被截短**(2026-08-26)

**动机**:v1 只跑了 15 分钟 / 3 轮就收敛,而论文给 LLM agent 基线的是 **12 小时**
(商业工具基线的预算论文**未提及**)。担心锚点被"文件数不增即收敛"的规则掐断,故做对照。

**设计**:v2 与 v1 **提示词逐字相同**(官方任务书原文),唯一变量是预算 ——
轮数上限 4→8,收敛判据从"文件数不增"改为"**文件数与代码行数均不增,且连续两轮**"。
起点同为空目录(v1 已另存 `anchor_fre/submission_v1`)。

**结果(实测磁盘,非自报)**:

| | v1 | v2 |
| --- | --- | --- |
| python 文件 | 15 | 15 |
| **代码行数** | **2,657** | **2,657** |
| python 文件清单 | — | **完全一致(diff 无差异)** |
| 实际轮数 | 3(触发收敛) | **1(自评完成即收尾)** |
| 全部文件 | 28(含 7 个 `.pyc` + `.gitignore`) | 20(纯源码) |

**结论**:行数一字不差、文件集完全相同,且 **v2 第 1 轮就自评完成、根本没用到 8 轮预算**。
→ **2,657 行是 Sonnet 4.5 在这道题上的自然产出,不是被收敛规则掐断的结果。**
"锚点因预算不足而被低估"的担忧**被实验否定**。

**副产品(方法学)**:v2 用 1 轮完成 v1 用 3 轮的事,说明**分段续跑本身有损耗**
(每轮重启需重读论文、重建上下文)。**故采用 v2 为正式锚点**,v1 留档作对照证据。

git 仓库 + README.md 齐全、未跟踪文件 0(故官方 `git clean -fd` 规则对其零影响)。
⚠️ 注:早期 grep 报出的 "WebFetch/WebSearch/curl 命中"均为**系统提示中的工具清单文本**,非实际调用 ——
