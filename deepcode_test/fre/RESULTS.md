## 3. 丢分在哪:高度集中,不是均匀劣势

### 3a. 三个一级维度(权重均为 3)

### 3b. 方法实现细目 —— 真正的病灶

| 细目(权重) | bare_v4 | trial1 | trial5 | anchor |
| --- | --- | --- | --- | --- |
| FRE 主模型 (3) | 0.815 | 0.824 | 0.685 | 0.917 |
| GC-IQL (1) | 0.667 | **0.000** | **0.000** | 1.000 |
| GC-BC (1) | 0.800 | **0.000** | **0.000** | 1.000 |
| OPAL (1) | 0.944 | **0.000** | **0.000** | 0.000 |

**DeepCode 两轮都没写任何对比基线**,文件清单直接证实:

```
bare_v4 : baselines/gc_bc.py  gc_iql.py  opal.py  fb_sf.py    ← 4 个基线
anchor  : baselines/gc_bc.py  gc_iql.py                       ← 2 个(所以 OPAL 得 0)
trial1  : fre/models/ fre/training/ fre/reward_functions/ …   ← 基线文件 0 个
trial5  : models/ rewards/ training/ data/ evaluation/ …      ← 基线文件 0 个
```

**机制**:`CodePlannerAgent` 在 Phase 5 一次性定死文件树,写码循环只负责把树上的空壳填满。
规划时漏掉的东西,后面几百轮写码永远补不回来 —— 这是"计划-填充"架构的结构性缺陷。
裸跑的 Claude Code 边读论文边决定写什么,读到 baselines 章节自然就写了。

| trial1 | 0.5184 | **0.6524** |
| trial5 | 0.4246 | **0.5585** |

trial1 补上后是裸跑的 **1.354×** —— 与论文声称的 **1.34×** 几乎一致。

**→ 论文的架构增益可能是真的,只是被规划器的一次遗漏整个吃掉了。**

## 3d. 归因辨析:丢分的两条独立链条

发现预筛器静默失效(见 `docs/FINDING_prefilter_silent_failure.md`)后,
曾怀疑低分主要由它造成。**查证结论:不是主因**,两条证据:

**证据一 —— 时序上不可能。** 日志显示规划先于索引:

```
21:17:12  ✅ Successfully extracted file tree from initial plan   ← 文件树在此定死
21:17:12  🚀 Starting code indexing process                       ← 索引才开始
```

预筛 bug 发生在索引阶段(Phase 8),而基线三项全 0 是**文件树里没有这些文件**造成的,
该决定在 Phase 5 就做完了。直接验证 `initial_plan.txt`:

| 轮次 | plan 里提到基线 |
| --- | --- |
| trial1(0.5184) | 2 次,且都在散文里("和 baselines 比较"),**非文件树条目** |
| trial5(0.4246) | **0 次** |

**证据二 —— 失效率与分数不相关。**

| 轮次 | 预筛失效率 | 得分 |
| --- | --- | --- |
| trial1 | **40%** | **0.5184**(最高) |
| trial3 | 20% | 0.4378 |
| trial5 | **40%** | 0.4246(最低) |

若"失效越多分越低",trial3 该最高。实际相反。n=3 很小,但方向不支持该假设。

**证据三 —— 机制上也说不通。** 检索实现是「全库打分 + 取前 10」
(`tools/code_reference_indexer.py:179-199`):

```python
for repo_name, index_data in index_cache.items():
    for ref in extract_code_references(index_data):
        relevance_score = calculate_relevance_score(target_file, ref, keywords)
        if relevance_score > 0.1:
            all_references.append((ref, relevance_score))
all_references.sort(key=lambda x: x[1], reverse=True)
return all_references[:max_results]      # max_results=10
```

预筛失败导致的是**库更大**,不是库更差 —— 全量索引是筛选结果的**超集**,
相关文件一定还在里面,不会丢信息。最多只能让某个无关卡片在排序里挤掉一个相关卡片,
且要挤进前 10 才有影响。

**结论**:
- **主因**:规划器漏掉对比基线 —— 三项权重各 1,占"方法实现"维度一半
- **预筛失效不是分数原因**:未观察到相关性,机制上也只能造成排序稀释而非信息丢失。
  它的**可确证代价是时间与成本** —— tianshou 一个仓库 239 vs 13 文件(18 倍),
  `google-research` 8,885 文件全量索引需约 140 小时,严重到让整轮跑不完(rice trial1 因此终止)

## 3e. 与论文数字的对照:可复现性不对称

| | 论文报的 | 我方实测 | 差距 |
| --- | --- | --- | --- |
| 裸 Claude Code | 0.6286 | **0.4839** | −0.145 |
| DeepCode | 0.8435 | **0.5184 / 0.4246** | −0.32 ~ −0.42 |

裸跑侧的 0.145 **几乎正好等于独立测得的裁判偏严幅度**(judge_eval:约 9pp),
即**论文的 Claude Code 数字基本可复现**。
DeepCode 侧差 0.32~0.42,是裁判偏移的两三倍 —— 同裁判、同论文、同 rubric,
**一边对得上、一边对不上**。

⚠️ **不可做数值校正**:锚点偏移 n=1,95% CI 宽达 ±0.499,且偏移在章节间高度不均
(I²=85.8%),**不是可加减的标量**。以下仅为数量级示意,不构成结论:
`0.5184 + 0.145 = 0.663`,即便再加上补全基线的反事实增量也只到约 0.797,仍够不到 0.8435。

**能说的**:论文 fre 的**绝对水平**可复现,**增益部分不可复现**。
**不能说的**:不能断定论文夸大 —— 混着三个拆不开的变量:
① 底座不同(论文 Sonnet 4.5 vs 我方 V4-Pro)
② 工程状态不同(开源版有预筛失效、下载无重试、规划漏基线等真实缺陷)
③ 裁判不同且偏移不可标量化

**②最值得强调**:若论文的 0.8435 跑在一个不存在这些缺陷的内部版本上,
则**开源出来的这份代码无法支撑论文的声称** —— 这是可陈述、可验证的结论。

## 4. 其他发现

**代码量与得分反相关**:trial5 写了 8,438 行(全场最多、是 bare_v4 的 2.7 倍),
得分 0.4246,反而低于 bare_v4 的 3,070 行 / 0.4817。写码循环里 `command_executor`
一次都没被调用 —— 只生成、不执行、不验证,多出来的代码只是多出来的猜测。

**轮间方差**:DeepCode+V4-Pro 完整轮跨度 0.094,小于论文自报的 0.15,量级一致。
主要来源是参考仓库提名的温度抖动 —— trial5 与 trial6 各提名 5 个仓库、4 个重合,
只差第 5 个(CQL 136 卡 ↔ exorl 16 卡),索引总量因此 245 卡 vs 121 卡。

**两条裸跑基线可比性(勿说过头)**:bare_v4 0.4817 与 anchor 0.4839 只差 0.0022,
但推不出"两个底座水平相同" —— 任务书不同(官方原文 vs 压缩版)、推进方式不同
(≤4 轮续跑 vs 单次)、耗时差 5 倍、bare_v4 仅 n=1。
可以说:同一口径下两条裸跑基线都落在 0.48 附近。主结论不依赖这条。
